    Qué es Hermes y para qué sirve

    Entender las piezas de un agente y qué hace distinto a Hermes antes de instalar nada.

    Hermes Agent es un agente de IA autónomo y open source publicado por Nous Research el 25 de febrero de 2026. No es un modelo: es el programa que rodea a un modelo (Claude, GPT, Gemini, Hermes 4, uno local…) y le da manos, memoria y presencia.

    Open source significa que el código es público (en GitHub) y puedes leerlo, instalarlo y modificarlo. El modelo es el que «piensa» y escribe texto; por sí solo no puede tocar tu ordenador. Hermes es el programa que le deja hacerlo.

    Un chatbot responde; un agente actúa en bucle: piensa, llama a una herramienta (terminal, ficheros, web, navegador, MCP…), lee el resultado y decide el siguiente paso hasta terminar. Una herramienta (tool) es una función concreta que el agente puede invocar: ejecutar un comando, leer un fichero, buscar en la web. MCP (Model Context Protocol) es un estándar abierto para enchufar herramientas externas (GitHub, una base de datos, un CRM…) a cualquier agente compatible. Hermes añade a ese bucle tres cosas que lo diferencian:

    • Vive fuera de tu sesión. Un proceso llamado gateway lo mantiene encendido en tu Mac o en un VPS (Virtual Private Server: un servidor alquilado en la nube que está siempre encendido), y puedes hablarle desde Telegram, Slack, Discord, WhatsApp, iMessage, email…
    • Aprende. Guarda memoria sobre ti y tu entorno, y convierte lo que resuelve en skills reutilizables que él mismo escribe y mejora.
    • Trabaja solo. Programa tareas con cron (el nombre clásico en Unix para «ejecutar algo a una hora fija o cada cierto tiempo»), recibe webhooks (avisos HTTP que otro servicio envía cuando pasa algo, p. ej. «se ha abierto un pull request») y entrega resultados donde le digas.

    Cómo leer el diagrama. A la izquierda, las formas de darle trabajo; en el centro, el bucle; a la derecha, lo que puede usar y dónde guarda lo que recuerda.

    • CLI · TUI · Desktop: CLI (Command Line Interface) es el chat en la terminal; TUI (Text User Interface) es una interfaz más rica dentro de la misma terminal; Desktop es la app de escritorio.
    • Cron · blueprints: tareas programadas; un blueprint es una plantilla de tarea programada lista para rellenar (comando /blueprint).
    • Webhooks · CI (hermes -z): CI (Integración Continua) son las automatizaciones que se ejecutan en cada cambio de un repositorio, como GitHub Actions. hermes -z es el modo «una pregunta, una respuesta y salir», pensado para scripts; lo verás en el módulo 02.
    • Editor (ACP) · MCP serve: ACP (Agent Client Protocol) permite usar Hermes dentro de editores como VS Code, Zed o JetBrains (hermes acp). hermes mcp serve hace lo contrario que conectar un MCP: expone Hermes como servidor MCP para que otros agentes lo usen.
    • AGENTS.md: fichero de instrucciones del proyecto que Hermes lee si está en la carpeta donde trabajas (convenciones, comandos, qué no tocar).
    • Modelo: OpenRouter, Anthropic, Nous…: son proveedores, las empresas que sirven el modelo por Internet. Te identificas con una API key (clave secreta) y pagas por uso.
    • Terminal: local · Docker · SSH · nube: dónde se ejecutan los comandos. Docker es un contenedor aislado; SSH es una conexión a otra máquina remota.
    • Subagentes (delegate_task): el agente puede lanzar otros agentes para tareas parciales; delegate_task es el nombre de esa herramienta.
    • ~/.hermes: ~ es tu carpeta personal (en Mac, /Users/tu-usuario). Ahí guarda Hermes todo su estado; el módulo 01 detalla cada carpeta.

    Para qué sirve bien

    • Un asistente personal o de equipo 24/7, accesible desde el móvil.
    • Automatizar trabajo recurrente: informes, vigilancia, resúmenes, triage.
    • Tareas de ofimática "describe el resultado": Excel, Word, PDF, carpetas.
    • Rodear tu trabajo de programación: CI, revisión de código, subagentes, entornos aislados.

    Para qué no es la mejor opción

    • Programar dentro del IDE (el editor de código, como VS Code) con el mejor agente de código posible (ahí ganan Claude Code o Codex; Hermes los puede orquestar, es decir, encargarles trabajo y recoger el resultado).
    • Flujos 100 % deterministas (misma entrada, mismo resultado, sin un modelo que decida) con cientos de integraciones (n8n, Zapier).
    • Usuarios no técnicos que no quieren tocar una terminal.
    Glosario rápido
    • Toolset: grupo de herramientas que el agente puede usar (file, terminal, web, browser…).
    • Skill: carpeta con un SKILL.md que explica un procedimiento. Estándar abierto compartido con Claude. El agente solo carga una skill cuando la tarea la necesita.
    • Memoria: notas que el agente guarda entre conversaciones (MEMORY.md sobre el entorno, USER.md sobre ti).
    • Sesión: una conversación guardada, con su historial; se puede retomar más tarde.
    • Gateway: proceso en segundo plano que conecta Hermes con mensajería y ejecuta el cron.
    • Backend de terminal: dónde se ejecutan los comandos (tu máquina, Docker, SSH, sandbox en la nube).
    • Perfil: un Hermes independiente con su propia config, memoria y skills (hermes -p trabajo; -p es la forma corta de --profile y elige el perfil llamado trabajo).

    Qué significa cada término de la tabla
    • Apple Silicon / Intel: los chips M1, M2… de Apple frente a los Mac antiguos con procesador Intel.
    • x86_64, ARM64, aarch64: arquitecturas de procesador. x86_64 es la de casi todos los PC; ARM64 y aarch64 son dos nombres de la misma arquitectura ARM de 64 bits.
    • glibc: la biblioteca básica de C de la mayoría de distribuciones Linux (Ubuntu, Debian, Fedora). Si tu distribución la usa, cumples este requisito.
    • WSL2: Windows Subsystem for Linux, un Linux real que corre dentro de Windows.
    • Tier 1: plataformas con soporte prioritario: el proyecto procura no romper nunca su instalación y sus fallos se corrigen primero.
    • MSIX: el formato de paquete de instalación moderno de Windows.
    • git, curl, tar, shasum/sha256sum: descargar el código, descargar ficheros, descomprimirlos y comprobar con una huella SHA-256 que lo descargado no está corrupto ni alterado.
    • sudo / libatomic1: sudo ejecuta un comando como administrador; libatomic1 es una biblioteca del sistema que el Node incluido necesita y que algunas distribuciones mínimas no traen.
    • uv, ripgrep, FFmpeg, Chromium: gestor de entornos de Python, buscador de texto muy rápido, conversor de audio y vídeo, y el navegador que el agente controla.
    • Token y contexto: un token es un trozo de palabra (unos 4 caracteres en inglés); los proveedores cobran por tokens. El contexto es cuántos tokens puede tener el modelo a la vista a la vez: instrucciones, historial, resultados de herramientas. Hermes necesita al menos 64K (unos 64 000).
    • Ollama, llama.cpp y ctx-size: programas para ejecutar modelos en tu propia máquina. Por defecto suelen arrancar con un contexto menor; hay que subirlo: en llama.cpp con la opción --ctx-size y en Ollama con OLLAMA_CONTEXT_LENGTH o num_ctx.
    • API key: clave secreta que identifica tu cuenta ante el proveedor y con la que te cobra el uso. Trátala como una contraseña.

    El instalador trae su propio Python 3.14, Node, ripgrep, FFmpeg, uv y un Chromium para el navegador. No toca el Python de tu sistema. En nuestra prueba (Mac mini M-series) tardó unos 3 minutos y dejó instaladas 58 skills de serie.

    Opciones útiles: --non-interactive, --skip-browser, --skip-computer-use. Ojo: el instalador sigue la rama main (nuestra prueba quedó en v0.21.6+301); para fijar una versión exacta usa --commit <sha>.

    • --non-interactive: se salta los pasos que piden datos (asistente de configuración y gateway). Útil en servidores y scripts; luego configuras con los comandos de abajo.
    • --skip-browser: no instala las herramientas de navegador ni su Chromium (ahorra unos 330 MB).
    • --skip-computer-use: no instala el driver que permite al agente mover el ratón y teclear en tu escritorio.
    • main es la rama principal del repositorio en git: recibe cambios cada día, así que dos instalaciones hechas en días distintos pueden diferir. v0.21.6+301 se lee «la versión publicada v0.21.6 más 301 cambios (commits) posteriores».
    • --commit <sha>: el sha es el identificador de un commit (p. ej. 8bff64d). Fijarlo hace la instalación reproducible: todos los alumnos tienen exactamente el mismo código.

    Como el script llega por un pipe, las opciones se pasan así: curl -fsSL …/install.sh | bash -s -- --skip-browser. -s le dice a bash que lea el script de la entrada estándar y -- separa sus opciones de las del instalador.

    Dónde queda cada cosa

    árbol
    ~/.local/bin/hermes        ← lanzador (se añade al PATH en ~/.zprofile)
~/.hermes/
├── hermes-agent/          ← código fuente (git)
├── config.yaml            ← configuración sin secretos
├── .env                   ← API keys y tokens
├── SOUL.md                ← identidad y tono del agente
├── memories/              ← MEMORY.md y USER.md
├── skills/                ← skills incluidas, instaladas y creadas por el agente

    ~ es tu carpeta personal. Un nombre que empieza por punto (.hermes, .env) es oculto: no aparece en Finder ni con ls a secas, sí con ls -a.

    • PATH: la lista de carpetas donde la terminal busca los programas. Gracias a ella escribes hermes en lugar de ~/.local/bin/hermes.
    • ~/.zprofile: script que zsh (la terminal por defecto en macOS) ejecuta al abrir una sesión. El instalador añade ahí la línea que mete ~/.local/bin en el PATH; en Linux con bash el equivalente es ~/.bashrc.
    • Lanzador: un pequeño ejecutable que arranca el programa real, instalado en hermes-agent/.
    • config.yaml y .env: la configuración se separa en dos ficheros a propósito. config.yaml (formato YAML: claves y valores con sangría) guarda ajustes que puedes enseñar o copiar; .env guarda solo secretos, en líneas NOMBRE=valor (variables de entorno). Así compartes tu configuración sin filtrar claves.
    • SOUL.md: texto en Markdown que se le inyecta al agente en cada conversación para fijar su personalidad y tono.
    • checkpoints/: copias de los ficheros antes de que el agente los modifique, para poder deshacer. Solo se crean si activas los checkpoints; lo verás con /rollback en el módulo 02.

    Conectar un modelo (OpenRouter)

    hermes model     # asistente: elige OpenRouter, pega la clave, elige modelo
hermes setup     # asistente completo: modelo, terminal, gateway, herramientas

    OpenRouter es un intermediario: con una sola API key das acceso a modelos de muchas empresas (Anthropic, OpenAI, Google…) y pagas en una sola cuenta. Por eso lo usamos en el curso: cambiar de modelo no exige abrir otra cuenta. En hermes setup, «terminal» significa dónde se ejecutan los comandos (tu Mac, Docker, SSH…) y «gateway» la conexión con apps de mensajería; puedes dejarlos por defecto ahora.

    Antes de lanzar los asistentes

    Abre una terminal nueva tras instalar: el instalador añade Hermes al PATH en ~/.zprofile. hermes model y hermes setup son asistentes interactivos, así que necesitan una terminal real; desde un script, un pipe u otro agente usa la alternativa de abajo.

    Alternativa sin asistente. hermes config set decide el fichero según la clave: MAYÚSCULAS van a .env, rutas con puntos a config.yaml.

    # sintaxis: hermes config set <clave> <valor>
hermes config set OPENROUTER_API_KEY sk-or-...    # tu clave de OpenRouter (empieza por sk-or-) → ~/.hermes/.env
hermes config set model.provider openrouter        # qué proveedor usar → config.yaml, sección model
hermes config set model.default anthropic/claude-haiku-5.5   # modelo por defecto → config.yaml

    model.provider se lee «la clave provider dentro de la sección model» de config.yaml. El nombre del modelo sigue el formato de OpenRouter, empresa/modelo: aquí, Claude Haiku 5.5 de Anthropic, un modelo rápido y barato, adecuado para las pruebas. Para comprobar dónde ha quedado cada cosa: hermes config path y hermes config env-path imprimen la ruta de cada fichero, y hermes config get model muestra la sección.

    Comprobar

    hermes --version   # qué versión tienes instalada
hermes doctor      # revisa configuración y dependencias, y señala lo que falte
hermes -z "Responde solo: OK y tu modelo" --usage-file uso.json
# → OK. Soy Hermes Agent con anthropic/claude-haiku-5.5 vía OpenRouter.   (8 s, 0,0025 $)
cat uso.json       # muestra el informe de tokens y coste de esa llamada

    Qué significa cada parte de la tercera línea:

    • -z "…" (forma larga --oneshot): modo one-shot. Envía una sola pregunta, imprime solo la respuesta final y termina. Es la prueba más corta posible de que la clave, el proveedor y el modelo funcionan de punta a punta.
    • --usage-file uso.json: al acabar, Hermes escribe en uso.json un informe en formato JSON (texto estructurado en pares clave-valor, fácil de leer desde un script) con el modelo, los tokens de entrada y salida, el número de llamadas a la API y el coste estimado en dólares. Lo pedimos para saber cuánto cuesta cada prueba en lugar de suponerlo: de ahí sale la cifra 0,0025 $. El nombre uso.json es libre; el fichero se crea en la carpeta donde estés y se sobrescribe en cada ejecución. Solo funciona junto a -z, y se escribe incluso si la ejecución falla.

    Requisito del modelo: al menos 64K tokens de contexto. Actualizar: hermes update (descarga la última versión de main y reinstala dependencias; hermes update --check solo comprueba si hay una nueva). Copia de seguridad: hermes backup (crea un .zip con toda tu configuración, skills, sesiones y datos; incluye credenciales, así que guárdalo como guardarías una contraseña). Desinstalar: hermes uninstall --dry-run (ensayo: enseña lo que borraría sin borrar nada) y luego --full (lo borra todo, configuración y datos incluidos).

    Primeros pasos: modos y comandos

    probado

    Saber cuándo usar el chat interactivo y cuándo el modo one-shot para scripts.

    ModoComandoCuándo
    Interactivohermes · hermes --tuiTrabajo del día a día
    One-shothermes -z "…"Scripts, CI, pipes. Imprime solo la respuesta final
    One-shot con sesiónhermes chat -Q -q "…"Igual, y muestra el session_id para retomarla
    Desde stdin… | hermes chat -Q --query-file -Pasarle datos generados por otro comando
    • Interactivo: abres una conversación y vas escribiendo turno a turno. hermes abre la CLI clásica; hermes --tui abre la TUI, una interfaz más rica dentro de la misma terminal.
    • One-shot («de un tiro»): una pregunta, una respuesta y el programa termina. Como no espera a que escribas nada, sirve dentro de scripts, de CI (las automatizaciones de un repositorio, como GitHub Actions) o de tareas programadas.
    • Pipe (|): conecta la salida de un comando con la entrada del siguiente. A esa entrada se le llama stdin (entrada estándar).
    • hermes chat es el subcomando de conversación. -q "…" (--query) le da la pregunta; -Q (--quiet, «silencioso») quita banner, animación y avisos de herramientas, y responde y sale. Al final imprime el session_id, el identificador de la sesión guardada, que sirve para retomarla.
    • --query-file -: lee la pregunta de un fichero; el guion - significa «de stdin». Lo que llega por el pipe se toma tal cual, sin que la shell interprete comillas ni $.
    Cambio en v0.21

    hermes chat -q "…" en una terminal real abre una sesión interactiva con ese primer mensaje. Para que responda y salga añade -Q, --oneshot o usa -z.

hermes -t file,web -z "Resume https://hermes-agent.nousresearch.com en 3 viñetas"

hermes -c                 # (--continue) continúa la última sesión
hermes --resume <id>      # retoma una sesión concreta por su session_id
    Por qué -t file,web

    Un toolset es un grupo de herramientas. file trae leer, escribir, editar y buscar ficheros; web trae buscar en Internet y extraer el contenido de una página. Con -t file,web el agente solo tiene esos dos grupos para esta ejecución: no tiene terminal, ni navegador, ni la herramienta de memoria. Para resumir una web no necesita más, y cuantas menos herramientas tiene, menos puede hacer fuera de lo que pides (eso es la superficie mínima) y menos texto de definiciones de herramientas se envía al modelo. Sin -t, usa los toolsets activados en tu configuración; hermes tools list te los enseña todos.

    Slash commands que vas a usar a diario

    Un slash command es una orden que escribes dentro del chat interactivo empezando por /. No se envía al modelo: la ejecuta Hermes directamente.

    ComandoPara qué
    Ctrl+P · /helpPaleta de comandos y ayuda
    /model · /reasoning highCambiar de modelo y de nivel de razonamiento
    /new · /resume · /sessionsGestionar conversaciones
    /usage · /context · /compressCoste, contexto ocupado y compactarlo
    /planQue piense un plan antes de tocar nada
    /goal <objetivo>Bucle hasta cumplirlo, con un modelo juez
    /bg <tarea> · /agents · /steerTrabajo en segundo plano y subagentes en vivo
    /rollback · /diffDeshacer cambios en ficheros
    /memory · /skills · /toolsVer lo que sabe y lo que puede usar
    /yoloQuitar aprobaciones. Solo en un entorno aislado

    Qué hay detrás de cada fila:

    • Paleta de comandos (Ctrl+P): buscador de todos los comandos y skills; escribes unas letras y eliges.
    • Nivel de razonamiento: cuánto «piensa» el modelo antes de responder (none, minimal, low, medium, high, xhigh, max, ultra). Más nivel suele dar mejores respuestas en tareas difíciles, a cambio de más tiempo y más tokens.
    • Contexto y /compress: /context enseña qué parte de la ventana de contexto del modelo está ocupada; /compress resume la conversación para liberar espacio sin empezar de cero.
    • /plan: escribe un plan en Markdown en .hermes/plans/ dentro de la carpeta de trabajo, sin ejecutar nada. Lo revisas y luego le pides que lo ejecute.
    • /goal: tras cada turno, un segundo modelo (el juez) decide si el objetivo está cumplido; si no, Hermes sigue trabajando solo, con un límite de turnos.
    • /bg, /agents, /steer: /bg lanza una tarea en una sesión aparte y te deja seguir; /agents lista las tareas y subagentes en marcha; /steer le añade una indicación al agente mientras trabaja, sin interrumpirlo.
    • /diff y /rollback: /diff muestra los cambios de ficheros según git; /rollback restaura una copia anterior desde ~/.hermes/checkpoints/. Esas copias solo se hacen si los checkpoints están activados (hermes chat --checkpoints o checkpoints.enabled: true en config.yaml).
    • Aprobaciones y /yolo: antes de un comando peligroso (borrar, sobrescribir…) Hermes te pide permiso. /yolo quita esas preguntas; por eso solo tiene sentido en un entorno aislado, donde un error no puede dañar nada importante.
    03

    Hermes en la oficina

    probado

    Describir el resultado que quieres y dejar que Hermes elija las herramientas: Excel, Word, carpetas.

    Hermes trae skills para docx, xlsx, pptx, pdf, Google Workspace, Notion, Airtable, Obsidian, Apple Notes/Reminders y correo. No hay que programar: el truco está en escribir el prompt como un encargo a un becario muy rápido: formato de salida, restricciones y qué hacer ante la duda. Ficheros en 02-ofimatica/.

    Una skill es un paquete de instrucciones (a veces con scripts) que enseña al agente a hacer una tarea concreta, por ejemplo crear un .docx. Las de serie viven en ~/.hermes/skills/, agrupadas por categoría (productivity/docx, productivity/xlsx…). No tienes que nombrarlas: Hermes lee la descripción de cada una y elige la que encaja con tu encargo. Luego la ejecuta con sus herramientas: leer y escribir ficheros y lanzar comandos en el terminal.     Memoria persistente

    Cada sesión con un modelo empieza en blanco: solo «sabe» lo que va en su contexto, el texto que recibe en esa llamada (instrucciones, conversación, ficheros leídos). Ese texto se mide en tokens, trozos de palabra por los que pagas y que tienen un tope. La memoria de Hermes son dos ficheros de texto que se añaden al contexto al empezar cada sesión. Viven en ~/.hermes/, la carpeta de Hermes dentro de tu carpeta personal (~).

    memories/MEMORY.mdLo que ha aprendido de tu entorno≈ 2.200 caracteres

    Por qué tienen límite: se cargan en todas las sesiones, así que cada carácter ocupa contexto y cuesta tokens siempre. Hermes guarda ahí solo lo esencial; para lo demás busca en el historial (más abajo).

    • Por qué dos llamadas separadas: cada -z es una sesión nueva, sin la conversación anterior. Si la segunda acierta el formato, solo puede ser por la memoria.
    • cat muestra un fichero en el terminal. § es el separador que usa Hermes entre una entrada de memoria y la siguiente.

    Se inyecta al inicio de cada sesión, también en cron (las tareas programadas): nuestro job programado del módulo 5 formateó los importes así sin pedírselo. Para el historial completo el agente usa session_search, una de sus herramientas: busca por texto en las sesiones pasadas, que Hermes guarda en una base de datos local (SQLite). Dentro del chat, /memory muestra las escrituras de memoria pendientes de aprobar (ver «Higiene», más abajo).

    Automatización: cron y blueprints

    probado

    Programar trabajo recurrente, con o sin LLM, y elegir dónde llega el resultado.

    Tres palabras para empezar. Un job es una tarea programada: qué hacer y cuándo. Cron es el nombre clásico de Unix para el programador de tareas, y Hermes lo usa para su propio programador. El gateway es un proceso de Hermes que vive en segundo plano: conecta la mensajería (módulo 06) y, cada 60 s, revisa el calendario y lanza los jobs que tocan. Sin gateway los jobs se crean pero no se ejecutan solos (Hermes te lo avisa al crearlos).

    hermes gateway install && hermes gateway start    # launchd en macOS, systemd en Linux
hermes cron status                                  # ¿está vivo el programador?

hermes cron create "every monday 9am" \
  "Lee /ruta/gastos_T3_2026.csv y dame en 3 viñetas el total y la categoría con más gasto." \
  --name resumen-gastos-semanal --deliver telegram

hermes cron list
hermes cron run <id>        # dispararlo ya, para probar

    Qué significa cada parte:

    • gateway install registra el gateway como servicio del sistema; gateway start lo arranca. launchd (macOS) y systemd (Linux) son los gestores de servicios del sistema operativo: lo mantienen vivo y lo relanzan al reiniciar. Así los jobs corren aunque cierres la terminal. && ejecuta el segundo comando solo si el primero termina bien.
    • cron create recibe dos argumentos entre comillas: el horario ("every monday 9am", cada lunes a las 9) y el prompt, la instrucción que el agente ejecutará cada vez. El prompt debe valerse solo: el job no ve tu conversación, por eso la ruta al CSV es absoluta.
    • La \ al final de línea solo parte un comando largo en varias líneas; la shell lo lee como uno.
    • --name le pone un nombre legible. --deliver dice adónde llega el resultado (ver «Destinos»). Si no lo pones, el resultado se guarda en local.
    • cron list muestra los jobs con su id (12 caracteres) y su próxima ejecución. cron run <id> lo pone en cola para el siguiente repaso del programador (como mucho 60 s), sin esperar a su hora.

    Horarios

    • Una vez: in 30m (dentro de 30 minutos), 2026-11-03T09:00:00 (fecha y hora exactas, formato ISO)
    • Intervalo: 30m, every 2h (cada 30 minutos, cada 2 horas)
    • Natural: weekdays at 9am (laborables a las 9), daily at 7am
    • Cron: 0 9 * * 1-5

    Destinos (--deliver)

    • local → ~/.hermes/cron/output/
    • telegram, discord:#canal, slack, email
    • origin: el chat donde lo pediste
    • Si no hay nada nuevo responde [SILENT] y no envía nada

    La expresión cron clásica tiene cinco campos separados por espacios: minuto, hora, día del mes, mes y día de la semana. * significa «cualquiera» y 1-5 es un rango (lunes a viernes; 0 es domingo). Así, 0 9 * * 1-5 se lee «en el minuto 0 de las 9, cualquier día del mes, cualquier mes, de lunes a viernes»: lo mismo que weekdays at 9am.

    En los destinos, ~ es tu carpeta de usuario y ~/.hermes/ es la carpeta (oculta, por el punto) donde Hermes guarda su configuración, sus jobs y sus salidas. [SILENT] es una palabra de control: en un job con LLM, el agente la responde cuando no hay nada nuevo que contar, y Hermes entonces no envía nada. Así un resumen diario no te manda mensajes vacíos.

    Watchdog sin LLM: coste cero

    Un watchdog (perro guardián) es un vigilante: comprueba algo cada cierto tiempo y solo avisa si hay un problema. Para eso no hace falta un modelo de lenguaje (LLM): basta un script. Sin LLM no se gastan tokens, así que cuesta cero.

    mkdir -p ~/.hermes/scripts                # la carpeta de scripts de cron (-p: créala si no existe)
cp scripts/espacio_disco.sh ~/.hermes/scripts/
hermes cron create "every 1h" --name watchdog-disco --no-agent --script espacio_disco.sh --deliver telegram
# el script solo imprime si el disco supera el 85 %: salida vacía = no se notifica
    • --script espacio_disco.sh: el nombre de un script que está en ~/.hermes/scripts/. Hermes solo ejecuta scripts de esa carpeta: así sabes exactamente qué código puede lanzar un job. Los .sh se ejecutan con bash; el resto, con Python.
    • --no-agent: no se llama al modelo. El script es el job y lo que imprime (su salida estándar, stdout) se envía tal cual. Si no imprime nada, no llega ningún mensaje.
    • El script mira el uso del disco con df y solo imprime si pasa del umbral. El 85 % es un valor por defecto que deja margen para reaccionar; se cambia dentro del script (variable UMBRAL).

    Sin --no-agent, la salida del script se inyecta en el prompt: el script recoge datos y el modelo los interpreta.

    Lo que vimos en la prueba

    El job con LLM devolvió cifras exactas y aplicó la memoria (formato 1.234,56 €). También vimos la seguridad desatendida: en cron los comandos de terminal que necesitan aprobación se deniegan, así que el agente calculó sin ejecutar su script y lo avisó.

    «Desatendida» significa que nadie está mirando: en un job no hay una persona que pulse «aprobar», así que Hermes deniega por defecto lo que pediría permiso en un chat. Si un job necesita ejecutar algo, dale un script con --script: ese código lo has revisado tú.

hermes cron runs <id>      # historial de ejecuciones: cuándo corrió y cómo acabó

    Disparo único tras un despliegue

    Un job de una sola vez sirve para encadenar trabajo a algo que tarda: despliegas una preview, sabes que tarda unos minutos y programas la comprobación para cuando esté lista. Al ejecutarse, el job se borra solo.

    Una preview es una versión de prueba de tu app publicada para revisarla antes de darla por buena. La comprobación es un smoke test (prueba de humo): una verificación rápida de que lo básico funciona, sin entrar en detalle.

    cp scripts/smoke_despliegue.sh ~/.hermes/scripts/   # la URL se fija dentro del script

# → ✅ http://127.0.0.1:8765 responde: 6 productos en el catálogo   (llegó al móvil)
    • "in 5m": una sola vez, dentro de 5 minutos. smoke-pr-42 es solo un nombre: la comprobación del pull request (PR) número 42 de tu proyecto.
    • El script hace dos peticiones con curl: /salud (¿está viva la app?) y /api/productos (¿devuelve datos?). Cuenta los productos e imprime una línea con ✅ o ❌. 127.0.0.1:8765 es tu propia máquina, puerto 8765: la tienda de ejemplo del módulo 10.
    • Por qué la URL va escrita en el script: el script lo ejecuta el gateway, no tu terminal. Una variable de entorno que pongas en tu shell al crear el job no le llega.

    Sin --no-agent, el mismo job puede lanzar un agente que abra la URL en el navegador y recorra la feature: el E2E del módulo 10, disparado por el despliegue. E2E (end to end, de extremo a extremo) es una prueba que usa la app como lo haría una persona.

    MCP: tus propias herramientas

    probado

    Construir un servidor MCP en unas 50 líneas de código y conectarlo a Hermes (y a cualquier otro agente).

    MCP (Model Context Protocol) es el estándar para dar herramientas a un agente. Un servidor MCP es un programa pequeño que anuncia sus herramientas (nombre, descripción y parámetros) y las ejecuta cuando el agente las llama. El mismo servidor sirve para Hermes, Claude Desktop, Claude Code o Cursor: lo escribes una vez y lo conecta cualquier cliente MCP. El nuestro expone el inventario de una tienda guardado en SQLite, una base de datos que vive en un único fichero (tienda.db, que el servidor crea junto al script la primera vez que arranca, con cinco productos de ejemplo).

    07-mcp/servidor_tienda.py (extracto)
    # /// script                      ← metadatos del script (formato PEP 723)
# dependencies = ["mcp>=2.3"]     ← uv instala esto solo, al ejecutarlo
# ///
from mcp.server.mcpserver import MCPServer   # mcp 2.x (en 1.x: FastMCP)

mcp = MCPServer("tienda")           # nombre con el que se presenta el servidor

@mcp.tool()                          # convierte la función en una herramienta MCP
def stock_bajo() -> str:
    """Productos con stock estrictamente por debajo de su mínimo."""   # ← lo lee el modelo
    ...

@mcp.tool()
def registrar_pedido(sku: str, unidades: int) -> str:   # los tipos definen los parámetros
    """Registra una venta y descuenta el stock."""
    ...

if __name__ == "__main__":
    mcp.run()                        # escucha por stdio (entrada/salida estándar)

    Qué significa cada parte:

    • El bloque # /// script declara las dependencias dentro del propio fichero. Con uv run servidor_tienda.py, uv (el gestor de paquetes de Python que usamos en el curso) crea un entorno aislado con mcp y lo ejecuta. Así no hay requirements.txt ni pip install previo: el servidor es un solo fichero que se puede copiar.
    • @mcp.tool() publica la función como herramienta. El SDK lee la docstring (el texto entre """) como descripción y la firma (sku: str, unidades: int) como esquema de parámetros. El modelo decide cuándo llamar a cada herramienta solo por esa descripción, así que escríbela como una instrucción clara.
    • SKU es el código interno de cada producto (TEC-01 es el teclado). El fichero completo trae una tercera herramienta, listar_productos.
    • stdio es el transporte más simple de MCP: el cliente (Hermes) arranca el servidor como un proceso hijo y hablan por su entrada y salida estándar. No hay puertos ni red; el servidor vive mientras lo usa el agente.
    SDK de MCP 2.x

    Este servidor usa la versión actual del SDK oficial, la 2.x, donde la clase se llama MCPServer. En la 1.x se llamaba FastMCP: si sigues un tutorial de 2025 y ves ModuleNotFoundError, es por eso. Fija la versión en las dependencias del script.

    probado

    Separar el cerebro (modelo) de las manos (entorno) y preparar el entorno para que el agente rinda.

    Un agente programador rinde tanto como el entorno que le das: dónde ejecuta, qué ve, qué herramientas tiene y cómo comprueba su trabajo. Invertir en eso suele dar más que acumular skills.

    Cuatro decisiones de diseño

    • La config va dentro de la imagen, no montada. /opt/data (el HERMES_HOME) es un VOLUME de la imagen y Hermes escribe en él su estado: skills incluidas, cachés, state.db, los entornos que monte el agente… Si montas ahí la carpeta del equipo, la ensucias con decenas de MB en cada tarea. Copiada en la imagen, cada docker run --rm parte de cero y lo tira todo al acabar.
    • La imagen lleva las herramientas de tus repos. Si AGENTS.md dice uv run pytest, uv tiene que estar en la imagen; si no, el agente improvisa (un venv con pip en cada tarea) y deja de ejecutar lo que el repo indica.
    • La clave nunca va en la imagen. Entra al ejecutar, y solo la del proveedor, no el .env entero. Hermes no la escribe en disco: en auth.json guarda solo su huella.
    • Decide dónde va la visibilidad. Con --rm se van también las sesiones y hermes insights. Monta solo logs/ y sessions/ en un volumen, envía la salida a tu sistema de logs o mide el coste con el consumo de la clave en el proveedor, como hicimos aquí.

    Términos de esta lista: VOLUME es la instrucción del Dockerfile que declara una carpeta como volumen. state.db es la base de datos donde Hermes guarda sesiones e historial. AGENTS.md es el fichero del repositorio con las instrucciones para agentes (cómo instalar, cómo pasar los tests), que viste en el módulo 07. Un venv es un entorno virtual de Python creado a mano con pip, justo lo que uv automatiza. auth.json es el fichero de credenciales de Hermes; la «huella» es un resumen que identifica la clave sin permitir reconstruirla. hermes insights muestra estadísticas de uso a partir de las sesiones guardadas.

    Revisión de código en pre-push o CI

    Un diff es la lista de líneas añadidas y quitadas entre dos versiones del código. La idea: pasarle a Hermes el diff de tus cambios y que diga si hay algo bloqueante. Puedes lanzarlo como hook pre-push (un script que git ejecuta antes de cada git push y que cancela el envío si termina con error) o en CI (Integración Continua: automatizaciones que corren en cada cambio del repositorio).

    08-entornos/ci/revisar-diff.sh (núcleo)
    DIFF="$(git diff "$BASE" -- .)"        # cambios respecto a la rama base (main por defecto)
RESULTADO="$(hermes -t file -z "Revisa SOLO este diff... VEREDICTO: OK | BLOQUEANTE ... $DIFF" \
             --usage-file .hermes-review-usage.json)"
grep -q "VEREDICTO: BLOQUEANTE" <<<"$RESULTADO" && exit 1   # error = push cancelado

    Con -t file el revisor no tiene terminal ni web. Coste medido: 0,003 $ por revisión.

    Qué es -t file

    -t es la forma corta de --toolsets: la lista, separada por comas, de los grupos de herramientas que tendrá el agente solo en esta ejecución (sin ella usa los que tengas activos en hermes tools). El toolset file incluye cuatro herramientas: read_file (leer), search_files (buscar en contenidos y nombres), write_file (escribir) y patch (editar un trozo). Fuera quedan terminal, web, browser y el resto. Para revisar código basta con leer, y un revisor sin terminal no puede ejecutar nada aunque el diff contenga instrucciones maliciosas.

    Por qué el entorno local no escala

    Mientras trabajas solo, tu portátil es el mejor sitio para el agente. El problema aparece cuando todo el equipo, incluida gente que no programa, quiere que los agentes implementen features o arreglen bugs:

    ProblemaQué pasa en la práctica
    Cada entorno divergeCada persona acumula memorias y skills distintas. Sale un modelo nuevo y "a mí no me va": el arnés viejo lo frena
    Las skills no fuerzan el procesoSi el modelo no detecta que debe usar la skill, no la usa. "Ya lo tengo hecho"… sobre una rama vieja
    Mantener a mano no escalaRepartir skills o plugins y comprobar que todos los tienen al día es un trabajo en sí mismo
    RecursosBase de datos, Redis (un almacén de datos en memoria) y navegador no caben en el portátil pequeño de alguien de ventas
    Cero visibilidadUn agente en una terminal remota no te dice qué pasó en cada fase

    La salida no es escribir "mejores skills", sino montar un entorno compartido, controlado por el equipo técnico, igual para todos y observable. Hermes trae las piezas: perfiles, tablero kanban con dispatcher, /goal, revisión nativa, cron, mensajería y dashboard.

    Antes de seguir, el vocabulario que usa todo el módulo:

    Cómo leer esta tabla:

    • <rol> e <id> son huecos: pones el nombre de un perfil (revisor) o el id que devuelve el tablero al crear una tarjeta.
    • --clone copia del perfil activo su config.yaml, .env, SOUL.md y skills. Así el perfil nuevo hereda proveedor, modelo y clave. Los tokens de los bots de mensajería no se copian.

    • kanban_request_review, kanban_request_changes y kanban_complete no son comandos de terminal: son herramientas que el propio agente llama desde su tarjeta.     • El "resumen estructurado" que recibe cada fase es lo que la anterior dejó al cerrar: un summary en texto y un metadata con datos (criterios, ficheros cambiados, deuda…).
    • Una skill de proyecto vive dentro del repo (.hermes/skills/), no en tu ~/.hermes. Como cualquiera puede meter ficheros en un repo, Hermes no las carga hasta que confías en él con hermes skills trust <ruta>. La confianza se guarda en la configuración de cada perfil.

    Claves de diseño del pipeline

    La tarjeta dice QUÉ; el SOUL.md dice CÓMO

    Con --goal, un juez revisa cada turno del worker contra el título y el cuerpo de la tarjeta, y no deja terminar hasta que se cumpla. Todo lo que escribas en la tarjeta se convierte en objetivo: si pones "cuando esté en verde, pide revisión con kanban_request_review", el juez exigirá esa llamada como parte del resultado y rechazará el paso a revisión. Por eso la tarjeta lleva solo el objetivo y los criterios ("Hecho cuando: criterios cumplidos y pytest en verde") y el procedimiento (TDD, commit, pedir revisión) vive en el SOUL.md del perfil.

    Cada fase sabe qué validan las demás

    Un revisor riguroso pedirá tests para todo lo que vea sin cubrir, también para lo visual que la fase E2E va a comprobar en el navegador. Si el SOUL.md del revisor dice "lo visual lo valida el E2E", te ahorras rondas. En la ejecución de abajo lo dejamos sin esa línea para que veas el bucle de cambios en acción.

    Grabar el E2E: navegador clásico

    Desde la v0.21 el navegador por defecto es browser_exec (Browser Use), y browser.record_sessions solo graba con las herramientas clásicas (browser_navigate, browser_click…). Por eso crear-perfiles.sh pone browser.backend: off en el perfil e2e. La grabación es evidencia, no una demo: el agente verifica leyendo el DOM y el vídeo sale casi estático. Si quieres un vídeo para enseñar al equipo, añade una fase aparte con un recorrido de usuario lento y, si quieres, narración con text_to_speech y ffmpeg.

    Qué es cada cosa: browser_exec es una sola herramienta que maneja el navegador a través de Browser Use; las clásicas son una herramienta por acción (navegar, pulsar, escribir). browser.record_sessions: true graba cada sesión de navegador en vídeo WebM. browser.backend: off no apaga el navegador: fuerza las herramientas clásicas. El DOM es la estructura de la página (sus elementos y textos), que el agente lee en lugar de mirar la imagen. text_to_speech es la herramienta de voz de Hermes y ffmpeg, un programa para montar audio y vídeo.

    Requisitos: uv, jq y git. uv gestiona proyectos de Python: uv run pytest -q ejecuta los tests con el Python y las dependencias del proyecto, sin instalar nada a mano (pytest es el ejecutor de tests; -q, salida breve). jq lee JSON en la terminal: el script lo usa para sacar el id de cada tarjeta. Los perfiles se clonan de tu perfil activo, así que heredan proveedor, modelo y clave.

    Lo que hace crear-perfiles.sh con cada rol, tomando el revisor como ejemplo:

    crear-perfiles.sh (para un perfil)
    hermes profile create revisor --clone --no-alias --description "Revisa el diff…"

hermes -p revisor tools disable web memory delegation … browser vision

hermes -p revisor config set skills.write_approval true
    • -p <perfil> (o --profile) ejecuta cualquier comando de hermes contra ese perfil, sin cambiar el perfil activo.
    • --no-alias: sin esta opción, Hermes crea un comando con el nombre del perfil (por ejemplo, revisor) en ~/.local/bin. Aquí no hace falta: todo se lanza con -p o desde el tablero.
    • --description: una frase sobre qué hace el rol. El kanban la usa para repartir tareas por rol y no solo por nombre.
    • tools disable quita toolsets. Todos los perfiles pierden los que nadie necesita (web, image_gen, tts, computer_use, cronjob, delegation, memory, code_execution, connections, clarify, session_search). Especificador, implementador y revisor pierden además browser y vision: solo el e2e conserva el navegador. clarify sirve para hacer preguntas al usuario, y en una tarjeta nadie está mirando para contestar.
    • auxiliary.background_review.enabled false apaga la revisión en segundo plano que, tras cada turno, guarda memorias o corrige skills (el autoaprendizaje).
    • curator.enabled false apaga el mantenimiento automático que marca y archiva las skills que no se usan.
    • skills.write_approval true: cualquier cambio en una skill queda pendiente de tu aprobación.

    El porqué de esta "higiene": un equipo necesita que cada perfil se comporte igual el lunes que el viernes. Si aprendiera solo, cada ejecución partiría de un entorno distinto y no podrías comparar resultados.

    pipeline.sh (núcleo)
    SPEC=$(hermes kanban create "Especificar TIENDA-12" --assignee especificador \
  --workspace "dir:$WORK" --body "$TICKET …" --json | jq -r .id)
IMPL=$(hermes kanban create "Implementar TIENDA-12" --assignee implementador \
  --parent "$SPEC" --workspace "dir:$WORK" --goal --goal-max-turns 15 \
  --body "$TICKET  Hecho cuando: criterios cumplidos y pytest en verde." --json | jq -r .id)
hermes kanban create "E2E TIENDA-12" --assignee e2e --parent "$IMPL" --workspace "dir:$WORK" …

    Qué significa cada parte:

    • $WORK es la carpeta del repo nuevo (por defecto, una temporal creada con mktemp, como /tmp/tienda-a1B2) y $TICKET, el texto de ticket.md.
    • SPEC=$(…) guarda en la variable SPEC lo que imprime el comando. La \ al final de una línea indica que el comando sigue en la siguiente.
    • --workspace "dir:$WORK": el worker trabaja directamente en esa carpeta. Sin esta opción usaría una carpeta temporal vacía (scratch) y no vería la app.
    • --body: el encargo. Es lo que lee el worker y, con --goal, lo que evalúa el juez.
    • --json | jq -r .id: --json hace que el comando responda en JSON y jq -r .id extrae solo el campo id, sin comillas. Con ese id, la tarjeta siguiente se encadena con --parent.
    • --goal --goal-max-turns 15: el implementador trabaja en modo objetivo, con un máximo de 15 turnos (sin --goal-max-turns serían 20). Si se agotan, la tarjeta se bloquea para que la mire una persona.
    • En el script completo, cada tarjeta lleva también --max-runtime (10, 30 y 15 minutos): si un worker lo supera, el dispatcher lo para y devuelve la tarjeta a la cola.

    ¿Por qué un repo git nuevo en cada ejecución? Porque así todas parten del mismo estado; git deja ver el diff y hacer commits; y Hermes solo reconoce una carpeta como proyecto (y busca sus skills de proyecto) si tiene .git. Antes de crear las tarjetas, el script ejecuta hermes -p <perfil> skills trust "$WORK" para los cuatro perfiles.

Va en el repo y no en Hermes porque cómo se arranca un producto es cosa del producto: el flujo vive en Hermes; la ejecución, en el repo.

    Lecciones para montar el tuyo

    1. Céntrate menos en implementar y más en validar. Si al final tienes que revisar el código a mano, pregúntate qué validación falta: un test, una prueba de rendimiento si toca base de datos, un E2E.
    2. Decide qué es determinista. El orden de las fases lo fija un script; dentro de cada fase decide el modelo. Lo que pueda comprobar código, que no lo juzgue el modelo.
    3. Dale al agente el entorno completo de un desarrollador: base de datos propia por worktree (una copia de trabajo extra del repo, en otra carpeta y otra rama), logs, navegador. Sin eso solo puede hacer tests unitarios y "creer" que funciona.
    4. Permisos mínimos por rol. El revisor no necesita navegador; el especificador no necesita escribir. Un agente proactivo atascado se inventa rodeos. Ojo: un perfil no es un sandbox: quitar toolsets limita sus herramientas, pero con la terminal el agente puede hacer lo mismo que tu usuario.
    5. Tu arnés puede frenar al modelo. "Prioriza siempre lo más simple" tenía sentido con modelos que sobre-ingenierizaban; con los actuales puede empujarles a la solución peor (un timeout, esperar un tiempo fijo, donde tocaba un watcher, reaccionar cuando algo cambia). Revisa SOUL, AGENTS.md y skills cada vez que cambies de modelo.
    6. No sobre-especifiques el cómo. Fija el qué y los criterios. Con modelos baratos puedes pedir varias variantes y quedarte con la que mejor pase las validaciones.
    7. Código fácil de revisar, para humanos y agentes: módulos con interfaces claras y la complejidad dentro (deep modules). Se leen interfaces y solo se baja al detalle donde algo huele mal.
    8. Construye tu propio flujo. Este pipeline es un punto de partida: tu producto puede necesitar dos fases o quince. Empieza pequeño y añade la validación que falte.

    Hermes con método: SDD y puertas humanas

    probado

    Pasar de tickets a un contrato: requisitos aprobados, decisiones registradas con nombre y commit, y un agente que propone sin poder firmar nunca.

    En el módulo anterior el equipo de agentes valida contra criterios que escribe el propio especificador. Para un proyecto con cliente falta algo: qué se pidió, con ejemplos, y quién lo aprobó. Este módulo monta el método Specification-Driven Development como un arnés de Hermes, hermes-sdd, con una regla que lo ordena todo:

    Artículo 13

    El ejecutor nunca firma; el notario nunca decide; el orquestador nunca interpreta.

    SDD (Specification-Driven Development, desarrollo guiado por la especificación) significa que primero se escribe y se aprueba qué debe hacer el software, con ejemplos concretos, y después todo (plan, tareas, código, tests, aceptación) se justifica contra ese texto. Un arnés es el conjunto de scripts y piezas que rodea al agente para que trabaje con ese método: le da las etapas, le pone límites y registra lo que pasa. El método tiene una «constitución» de 12 artículos (la especificación manda, trazabilidad, un commit por tarea, tests primero…); hermes-sdd añade el artículo 13, que reparte el poder entre tres piezas que verás en la tabla de papeles. Así ninguna puede hacer el trabajo de otra.

    Vocabulario del módulo

    Aparecen muchos términos nuevos. Vuelve aquí cuando te pierdas.

    TérminoQué es aquí
    RequisitoUna cosa que el software debe hacer (REQ-F-001, funcional) o cumplir (REQ-NF, no funcional; REQ-C, restricción), con criterios de aceptación numerados (AC1, AC2…) y ejemplos con datos. Viven en requirements/REQUIREMENTS.md; lo que pidió el cliente con sus palabras, en requirements/CUSTOMER-NEEDS.md
    MustLa prioridad más alta de un requisito. La escala del método es Must have / Should have / Nice to have (inspirada en MoSCoW). Un Must sin cumplir impide la entrega
    ContratoLos requisitos aprobados por una persona. Es lo que se compromete a entregar
    FASEUn incremento del plan: un grupo de requisitos que se implementa y se acepta junto (FASE-0, FASE-1…). Se acepta o se rechaza entera
    RutaQué etapas opcionales necesita este proyecto (specs formales, auditoría, plan de tests, seguridad, UX…). La propone el ejecutor a partir de los requisitos y la confirma una persona
    PuertaEl punto donde el flujo se detiene hasta que una persona decide (🚪 en el diagrama). Llega como mensaje con botones
    EjecutorEl agente que hace el trabajo de cada etapa. Por defecto, Claude Code en modo no interactivo (claude -p: recibe una instrucción, trabaja y termina, sin conversación) con las skills del método
    Notariofirmar.sh: un script de bash sin LLM que aplica la decisión de una persona (registro, commit y tag)
    OrquestadorEl kanban de Hermes más lanzar.sh: crea las tarjetas de cada etapa y las encadena, sin leer ni interpretar su contenido
    Tablero, tarjeta, tramoEl kanban del módulo 10: un tablero por proyecto, una tarjeta por etapa. Un tramo es la serie de tarjetas que va de una puerta a la siguiente
    Tag anotadoUna etiqueta de git (git tag -a) que, además de señalar un commit, guarda un mensaje. El notario escribe en él quién aprobó, con qué rol, por qué canal y sobre qué commit
    GuardiaUn hook: un script que se ejecuta antes de cada comando del ejecutor y deniega los prohibidos (firmar, crear tags de aceptación, tocar el kanban, git push…)

    Cierre y entregaEl cierre comprueba el proyecto entero (todos los Must de todas las FASEs) con la puerta de calidad global; si pasa, se abre la puerta de entrega y su tag entrega-N
    GrabaciónUna ejecución real guardada (historial git y commits de cada etapa) que se puede reproducir sin LLM. El ejecutor que la reproduce se llama replay

    Los papeles

    PapelQuiénQué hace

    PreguntaLa puerta: tarjeta bloqueada sin assignee y mensaje con botonesEnseña primero lo que va mal y después lo que hay que decidir

    «Tarjeta bloqueada sin assignee» quiere decir que la tarjeta de la puerta no tiene perfil asignado: ningún worker del kanban la recoge, así que se queda parada hasta que una persona decide. «Persona autorizada» es alguien que figura en ~/.hermes/hermes-sdd/aprobadores.json, con su nombre, su rol y su identidad en cada canal (su id de Telegram, su usuario del Mac). Los «veredictos» son el resultado por requisito: VERIFIED (cada criterio tiene evidencia válida), FAILING (alguna prueba falla), MISSING (falta evidencia) o WAIVED (exento por decisión humana).

    el flujo de un proyecto
    requisitos ─▶ 🚪 ─▶ ruta ─▶ 🚪 ─▶ plan ─▶ tareas ─▶ 🚪 ─▶ implementar N ─▶ aceptar N ─▶ 🚪 ─▶ … ─▶ cierre ─▶ 🚪 entrega
    • requisitos → 🚪: el ejecutor escribe los requisitos (o usa los que ya tienes) y tú los apruebas. Queda el tag requirements-v1.0.
    • ruta → 🚪: propone qué etapas opcionales saltar y por qué; tú aceptas, pides el pipeline completo o ajustas.
    • plan → tareas → 🚪: divide el trabajo en FASEs y cada FASE en tareas (una tarea, un commit). Das conformidad al orden de entrega.
    • implementar N → aceptar N → 🚪: programa la FASE N con tests, calcula los veredictos y graba la demo. Tú aceptas o rechazas. Si rechazas, vuelve a implementar con tu motivo como prioridad. Se repite por cada FASE.
    • cierre → 🚪 entrega: comprueba el proyecto entero y te pide la entrega final.

    Las decisiones del ejecutor se clasifican: R, reversibles (decide con la opción recomendada y lo anota); C, las que tocan el contrato (pregunta por escrito con opciones A/B/C y sigue con lo demás; tú contestas en la puerta con un formulario de botones); H, humanas por constitución (aceptar, exenciones, editar un test que ya existía): nunca las toma.

    Por qué así: el ejecutor corre sin nadie delante (claude -p lanzado desde una tarjeta), así que una pregunta a mitad de etapa no la contestaría nadie. Ejemplos de R: el nombre de una función interna o el orden de las tareas. De C: un criterio ambiguo o dos requisitos que se contradicen; la pregunta va a .sdd/questions-<etapa>.md. En H, una exención (waiver) es aceptar que un requisito quede sin cumplir, con motivo; y un test que ya existía es evidencia del contrato: si el ejecutor pudiera reescribirlo, podría «aprobar» cambiando el examen.

    Claves de diseño

    1. Quien ejecuta no firma. Un ejecutor sin persona en la sesión no puede "confirmar" nada. Si el prompt dice "esto es la confirmación del cliente", la guardia del método debe frenarlo, y lo frena. La firma es un paso determinista que aplica la decisión que una persona tomó en su canal.
    2. La identidad sale del canal, no de un texto. Un comentario "DECISIÓN: acepto" puede escribirlo cualquier proceso que corra con tu usuario. El toque en un botón trae el id de quien pulsó; eso se registra, con el id del mensaje como prueba.
    3. Lo que se firma es lo que se vio. La puerta guarda el commit que enseñó; si el repo cambia antes de firmar, el notario se niega.
    4. El kanban tiene fronteras: respétalas. Los procesos que lanza un worker no pueden modificar el tablero; Hermes lo impide a propósito. Por eso las tarjetas de puerta las crea el gateway, no la etapa.
    5. Un modelo pequeño no estima probabilidades. Con Haiku, los factores de la ruta salieron en la banda de duda y la regla "duda = sí" pidió el pipeline completo para una CLI de una persona; con el modelo por defecto, ruta ligera. El modelo pequeño, para mover tarjetas; los juicios calibrados, a otro. (Cómo funciona: la ruta pregunta siete «factores», como ¿hay datos sensibles? o ¿varios tipos de usuario?, cada uno como una probabilidad de 0 a 1. Desde 0,65 cuenta como sí; hasta 0,35, como no; en medio está la banda de duda, que cuenta como sí.)
    6. No preguntes a mitad de etapa: clasifica. Así el ejecutor sacó dos contradicciones reales de los requisitos y las dejó como preguntas para la puerta, en lugar de resolverlas a escondidas.
    7. Las puertas de FASE no ven el proyecto entero. Las cuatro FASEs se aceptaron y aun así faltaban dos requisitos Must sin FASE asignada: hace falta un cierre con la puerta de calidad global antes de la entrega.
    8. Una puerta debe obligar a mirar. Primero las alertas, luego "Ver demo" y solo entonces Aceptar. Se mide cuánto pasó entre ver la demo y decidir: aceptar en 6 s es una señal de aprobación por inercia que el resumen avisa.
    9. El canal también necesita vigilancia. Log, latido, tiempos máximos y autorreparación, y un presupuesto de atención: un mensaje vivo por proyecto, resúmenes y horas de silencio en lugar de un aviso por cada tarjeta. (El latido es un fichero que el plugin reescribe en cada vuelta: si deja de actualizarse, el bucle se ha parado. El mensaje vivo es un único mensaje por proyecto que se edita en silencio en lugar de mandar uno nuevo. Por defecto hay resúmenes a las 08:30 y a las 19:00 y silencio de 22 a 8, en atencion.json.)
    10. Lo que el ejecutor deja a medias, a la vista y comprobado. En un cierre, el ejecutor repitió una medición y no hizo commit del registro; el notario se negó a firmar con el árbol sucio. El arnés commitea esos restos con un mensaje que lo dice, pero solo tras comprobar que los registros de decisiones solo crecieron y que lo nuevo lo escribió la CLI; si no, la etapa falla y lo ve una persona. Y abre una puerta nueva: nunca se "arregla" una puerta vieja, porque su commit ya no es el que se mostró. («Árbol sucio»: hay cambios en el repo sin commit, así que el commit mostrado no describe todo lo que hay.)
    11. La puerta es un dato; el canal, un adaptador. Telegram y el panel llaman al mismo núcleo, que lo valida todo en el servidor: un botón que la interfaz oculta («Aceptar» antes de ver la demo) también se rechaza si alguien lo llama a mano. Añadir Slack o email es escribir un adaptador, sin tocar el notario. (La puerta es un fichero JSON en ~/.hermes/hermes-sdd/puertas/; el núcleo es hsdd_nucleo.py, dentro del plugin.)
    12. La identidad tiene fuerza, y se registra. El id de Telegram no vale lo mismo que «el usuario de este Mac» del panel en modo local. Por eso el canal queda en el tag, y el panel rechaza las peticiones que no vengan de la propia máquina.
    13. El mantenimiento propone; la persona decide. La revisión periódica no arregla nada: abre una puerta con lo que encontró. Cada hallazgo tiene una clave que resume qué falla; así, lo ignorado con motivo no vuelve con cada commit.
    14. Citar no es firmar. Una guardia que bloquea cualquier mención de un registro bloquea también leerlo, compararlo, commitear lo que escribió la CLI o citarlo en un informe, y el ejecutor acaba dejando trabajo sin cerrar. La guardia busca invocaciones (fuera de comillas, en el segmento que empieza por el comando) y escrituras; lo que se le escape lo para la comprobación del arnés al cerrar la etapa. Dos capas, cada una con su trabajo. (Ejemplos de las pruebas del arnés: sed -n 2p acceptance/decisions.jsonl lee el registro y se permite; cat >> acceptance/decisions.jsonl escribe en él y se deniega. Un texto entre comillas que dice «sin accept record» solo menciona el comando y se permite; node "$SDD" accept record demo … lo invoca y se deniega.)
    15. Cada incidente se convierte en prueba. El intento de firma desde el ejecutor es el caso nº 1 de las pruebas del arnés; tests/todo.sh las pasa todas sin LLM antes de cualquier actualización. También la práctica reproducida comprueba que cada decisión registrada sea de quien practica: una grabación trae el trabajo, nunca las firmas.

    Qué garantiza y qué no

    Garantiza que nadie firma sin una decisión de una persona autorizada y que lo firmado es el commit mostrado: el canal, el acta del notario y el registro con su tag cuentan la misma historia. No garantiza quién sostenía el móvil ni resiste a alguien con tu sesión del sistema: el kanban, los registros y los tags son ficheros tuyos. Las guardias dificultan; solo el ejecutor en contenedor (módulo 9) o una firma con llave física lo impiden.

    El acta es el fichero que deja el notario por cada puerta (~/.hermes/hermes-sdd/actas/) con los pasos que hizo; si se corta a medias, la siguiente llamada sigue desde ahí. Una llave física es un dispositivo USB de seguridad con el que se firman los tags: sin tocarla, ningún proceso puede firmar.

    Operación diaria desde el chat: /puertas · /estado · /mantenimiento · /pausar [proyecto|todo] [ahora] · /reanudar · /anular. Si se agota la cuota de Claude, las etapas se aparcan y se reanudan solas. Las mismas puertas, en la pestaña Puertas SDD del panel.

    Quién es quién

    • OpenClaw: otro asistente personal open source que vive en tu máquina y te contesta por mensajería; es el competidor más directo de Hermes. Hermes trae hermes claw para migrar desde él.
    • Claude Desktop / Cowork: la app de escritorio de Claude. Cowork es su modo de trabajo autónomo sobre tus ficheros y conectores. Sus tareas programadas se ejecutan en tu ordenador.
    • Claude Code + rutinas: Claude Code es el agente de programación de Anthropic en la terminal o el IDE (el editor de código). Las rutinas son tareas de Claude Code que se ejecutan con horario en la nube de Anthropic, sin tu ordenador.
    • Codex CLI y Gemini CLI: los agentes de programación de terminal de OpenAI y de Google. «Vía CI» quiere decir que, para programarlos, los lanzas desde un sistema de integración continua (como GitHub Actions, módulo 9).
    • Cursor: un editor de código con agente integrado; sus agentes «en segundo plano» trabajan mientras tú sigues en el editor.
    • n8n y Zapier: automatización con flujos de cajas conectadas (nodos), donde cada paso está fijado de antemano: deterministas, hacen siempre lo mismo. Pueden incluir un paso de IA.
    • LangGraph y CrewAI: librerías de Python para programar tu propio agente. No son un producto listo: el cron, la mensajería o la memoria los escribes tú.

    A favor de Hermes

    • Open source MIT y sin atarte a un proveedor: cambias de modelo con un flag.
    • Siempre encendido en un VPS y accesible desde el móvil.
    • Memoria y skills que mejoran con el uso, en formato estándar.
    • Cron con entrega a donde quieras y watchdogs sin coste de LLM (vigilantes que solo ejecutan un script y avisan si hay un problema, módulo 5).
    • 7 backends de ejecución (dónde corren sus comandos: tu máquina, Docker, SSH…), subagentes (agentes hijos a los que delega tareas, también en paralelo) y MCP en los dos sentidos: usa servidores MCP y se ofrece como uno con hermes mcp serve (módulos 8 y 9).
    • Lee tu AGENTS.md/CLAUDE.md e importa tu config de Claude Code con hermes import-agent (módulo 7).
    • Perfiles, tablero kanban y revisión nativa para montar un equipo de agentes por fases (módulo 10), y puertas humanas con un método encima (módulo 11).
    • Barato con modelos eficientes: todas las pruebas de este curso con Hermes, ≈ 0,56 $ (sin contar Claude Code como ejecutor en el módulo 11).

    En contra

    • Va muy rápido: cientos de PRs (cambios propuestos al código) por versión; flags y docs cambian de una semana a otra.
    • Mucha superficie de ataque: muchas piezas expuestas (panel web, gateway, integraciones) por donde podría entrar un atacante. La v0.21.6 corrigió fallos en el dashboard, en filtros git de repos no confiables y en el gateway de email.
    • La calidad depende del modelo: con modelos pequeños falla más con herramientas y memoria.
    • Más técnico que Claude Desktop: el despliegue y la seguridad son tuyos.
    • Las herramientas MCP no pasan por las aprobaciones: Hermes pide permiso antes de comandos peligrosos en la terminal, pero no antes de usar una herramienta MCP (módulo 8).
    • Muy proactivo: si se atasca se inventa rodeos. Necesita límites y permisos acotados.
    • Interfaz del dashboard (el panel web, hermes dashboard) funcional pero básica.

    Si ya usas Claude Desktop y sus tareas programadas

    Claude Desktop es más cómodo y no hay nada que mantener, pero sus tareas programadas dependen de que tu ordenador esté encendido con la app abierta y solo usan Claude. Hermes cubre el hueco cuando quieres que el trabajo ocurra aunque cierres el portátil, que el resultado te llegue a Telegram o Slack, o que una tarea barata la haga un modelo barato.

    No es una elección exclusiva. Las skills tienen el mismo formato, un servidor MCP sirve a los dos, y hermes mcp serve te deja usar Hermes desde Claude Desktop: Hermes se presenta como un servidor MCP más (módulo 8).

    Local frente a remoto y compartido

    Para ti solo, el agente en tu portátil (Claude Desktop, Claude Code, Hermes local) es lo más cómodo. Cuando es un equipo el que delega trabajo, la pregunta cambia: ¿todos tienen el mismo entorno? ¿quién ve qué hizo el agente en cada fase? ¿qué pasa cuando el agente necesita una decisión y nadie está mirando?

    Ahí pesa lo que Hermes trae de serie (perfiles por rol, tablero con logs por fase, cron, mensajería y una tendencia a resolver por su cuenta en lugar de quedarse esperando permiso), frente a agentes de código pensados para una persona delante de la terminal. El coste: la infraestructura y la seguridad son tuyas. Lo ves montado en el módulo 10.
